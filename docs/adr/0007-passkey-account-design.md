# 7. Passkey account: WebAuthn verified on-chain, low-s enforced by us

Date: 2026-09-09 · Status: accepted · Implements ADR 2

## Context
ADR 2 chose ERC-4337 with a P256 validator. Building it surfaced three things
that are not obvious from the specs.

**A WebAuthn assertion is not a signature over the challenge.** The authenticator
signs `sha256(authenticatorData || sha256(clientDataJSON))`, and the challenge
appears only inside `clientDataJSON`, base64url encoded. A contract that verified
a bare P-256 signature over the challenge would accept signatures the
authenticator never produced for the operation in hand.

**The precompile does not enforce low-s.** Verified against Monad mainnet: for a
valid signature `(r, s)`, the high-s variant `(r, N - s)` *also* returns 1. So
one authorisation has two valid encodings unless we reject one.

**Forking Monad does not give you Monad's precompiles.** A fork copies state, not
execution rules. On Foundry 1.7 every P-256 test failed in the most misleading
way available: the staticcall succeeds and returns empty, which is
indistinguishable from an invalid signature.

## Decision
- Reconstruct and verify the full assertion in `WebAuthn.sol`: RP binding via
  `rpIdHash`, the UP and UV flags, `"type":"webauthn.get"`, and the exact
  base64url challenge — then the P-256 check over the reconstructed digest.
- `P256.verify` rejects `s > N/2`. Clients normalise before submitting, which is
  the WebAuthn library convention. `verifyMalleable` is kept for tests.
- Require **user verification**, not merely user presence. This account moves
  money; a tap is not enough, we want the biometric that proves who tapped.
- Do not parse JSON on-chain. The caller passes field offsets and we assert the
  exact expected bytes sit there. The signature covers the whole JSON, so the
  offsets only say where to look — they cannot be used to smuggle content. Bad
  offsets fail closed, which is fuzzed.
- `network = "monad"` in `foundry.toml`, and CI fails loudly on Foundry < 1.8.

## Consequences
- Tests need no RPC and no fork: 33 tests in ~0.5 s. The precompile, gas model
  and 128 KB size limit all come from local Monad execution.
- Test vectors are generated by `script/gen_webauthn_vector.py`, a pure-Python
  P-256 implementation, so fixtures are reproducible and auditable rather than
  pasted from an unverifiable source. The frozen fixture was independently
  confirmed by calling the live precompile on mainnet, and CI asserts it has not
  drifted from the constants in `WebAuthn.t.sol`.
- `ffi = true` is on, so the account tests can sign a `userOpHash` they only
  learn at runtime rather than replaying one fixture.
- **The mobile client must normalise s to the low half before submitting.**
  That obligation now belongs to Phase 1's Flutter work.
- Validation returns `SIG_VALIDATION_FAILED` and never reverts on a malformed
  signature: a revert in the 4337 validation phase fails the whole bundle and
  can get the sender banned by bundlers.
